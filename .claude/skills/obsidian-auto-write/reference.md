# Obsidian自動書き込み — 詳細リファレンス

Claude Code の `obsidian-auto-write` スキルと、Codex CLI の `AGENTS.md` の両方から参照される、判断基準と
実装手順の本体。どちらのツールで動いていても、このファイルに書かれたルールに従う。

**大前提**: このVaultは Obsidian・Codex・Claude Cowork で共有する「AI作業用Vault」であり、すでに
`00_START_HERE.md` とVault直下の `AGENTS.md` に運用ルールが定義されている。ここに書く内容はそのルールを
このリポジトリから参照しやすいよう写したものであり、正本はあくまでVault側にある。**Vaultに実際に触れる
環境であれば、書き込み前に必ず `00_START_HERE.md` とVault直下の `AGENTS.md` を実際に読み、ここに書かれた
内容と矛盾があればVault側を優先すること。**(このリポジトリのコピーは更新が遅れる可能性がある)

## 書き込みトリガーの判断基準

### 書く

- 仕様・設定・運用ルールの変更で、決定した理由まで含めて残す価値があるもの
  (例: 「なぜこのライブラリではなくこちらを選んだか」「なぜこの閾値にしたか」)
- セットアップ・デプロイ・障害対応など、手順を間違えるとやり直しが発生する複雑な作業をやり切った直後
- 過去のやり取りや `Session_log.md` を見て「これ前にもやったな」と気づいたとき(2回目が起きた時点で
  もう書く。3回目を待たない)
- ユーザーが明示的に「メモして」「Obsidianに書いて」「マニュアル化して」と言ったとき(無条件で書く)

### 書かない

- その場限りの雑談、確認だけで終わった質問
- git のコミットメッセージやPRの説明にすでに十分残っている情報をそのまま複製するだけのもの
- 単純作業の実行ログ(「ファイルをコピーした」程度の粒度)
- まだ確定していない検討中の案(仮説として書く場合は「仮説」であると明記した上で書く。断定は絶対にしない)

### 迷ったときの一行基準

「これを書かなかったら1ヶ月後に同じ調査・同じ議論をもう一度することになるか?」
なるなら書く。ならないなら書かない。書きすぎてノイズになった Session_log.md は、書かれていないより悪い。

## Vaultの実体

- **ローカル**: Obsidianアプリで直接開いているフォルダ。絶対パスは未確定(`~/Documents/New project/
  obsidian-codex-cowork-vault` である可能性が高いが、これは仮説であり確認が必要)。
- **GitHub**: `fujisan-0121/obsidian-codex-cowork-vault`(非公開リポジトリ)。説明文に「GitHub基軸」と
  ある通り、常時稼働のMac miniから自動でpushされる形で実際に同期されている。ローカルのVaultフォルダに
  `.git` があり、このリポジトリのクローンそのものである。

このVaultには**クライアントの財務情報や、M&A関連の非常にセンシティブな内容が含まれる**。`.gitignore`で
`*M&A*` / `*エクイティ交渉*` に一致するファイルとその他数点が明示的に除外されている。**このスキルを実行する
AI(Claude/Codex問わず)は、これらのファイルには絶対に触れない・読まない・内容を推測して書かない・
会話や別のリポジトリに内容を漏らさないこと。** これは他の安全ルールより上位の絶対条件として扱う。

## Vaultパス解決(ローカル実行時)

解決順序(`scripts/resolve-vault-path.sh` が実装している):

1. 環境変数 `OBSIDIAN_VAULT_PATH` が設定されていて、かつそのディレクトリが実在する → それを使う
2. 設定ファイル `~/.config/claude-obsidian/vault-path`(1行目にVaultの絶対パス)が存在し、
   その中身のディレクトリが実在する → それを使う
3. 推測候補パス(`~/Documents/New project/obsidian-codex-cowork-vault`)が実在し、かつ `.obsidian`
   フォルダも実在する(=本物のObsidian Vaultらしいと確認できた)場合 → それを使う
4. どれも無い場合、ローカルで対話できるならユーザーに一度だけVaultの絶対パスを尋ね、
   `~/.config/claude-obsidian/vault-path` に保存する(以後は聞かない)

`resolve-vault-path.sh` は解決できたパスを標準出力に1行で返し、終了コード0で終わる。解決できなければ
終了コード1で終わり、標準エラーに次に何をすべきかのヒントを出す。

## クラウドセッションでの書き込み手順(Vaultに直接触れない環境の場合)

ローカルのVaultフォルダに触れない環境(このリポジトリのようなクラウド上の隔離セッションなど)でも、
Vault実体がGitHubリポジトリ `fujisan-0121/obsidian-codex-cowork-vault` として同期されているため、
GitHub経由で `03_handoffs/Session_log.md` への追記を届けることができる。手順は次の通り:

1. `fujisan-0121/obsidian-codex-cowork-vault` をこのセッションのGitHubスコープに追加してクローンする
2. **新しいブランチを切る**(例: `session-log/2026-09-01-短い説明`)。**`main` ブランチには絶対に直接
   pushしない** — このVaultは機密性が高く、AIが書いた内容をユーザーが確認する前に本流へ混ぜてはいけない
3. `03_handoffs/Session_log.md` の末尾に、ローカル実行時と同じフォーマットで追記する(下記
   「Session_log.mdへの追記フォーマット」参照)
4. 追記内容と、それ以外の変更(他のファイル)が絶対に混ざらないようにする。このコミットで触るのは
   `Session_log.md` だけにする
5. コミットしてそのブランチだけをpushする。コミットメッセージにも機密情報(クライアント名の詳細、
   金額、M&A関連の話題など)を書かない、あくまで作業内容を一般的な言葉で
6. ユーザーに「Vaultリポジトリの `<ブランチ名>` にSession_log.mdへの追記をpushした、確認してmainに
   マージしてほしい」と伝える。PRを作るかどうかはユーザーの意向を確認してから判断する(勝手に作らない)
7. `.gitignore` に列挙されたM&A関連ファイルは、存在を確認する目的であっても開かない・読まない

この手順は、ユーザーが「クラウドからはブランチを切ってpushするところまでにしてほしい、mainへの反映は
必ず自分で確認する」と明示した方針に基づく。この方針を勝手に変えない。

## 書き込み前に必ず確認する優先順位

Vaultへの書き込み権限を得たら、内容を書く前に次の順で確認する。上にあるものほど優先度が高い。

1. **親プロジェクトのAGENTS.md** — `/Users/fujiwaraikki/Documents/New project/AGENTS.md`
   このVault自体のルールより優先される、全体の最上位ルール。存在すれば必ず読む。
   (環境によってこのパスが無い場合は、無いことを `Session_log.md` の確認事項に明記し、推測で進めない)
2. **Vault直下の `AGENTS.md`**(Vault自体の運用ルール。安全ルール・MARKELINE参照ルール・
   `02_reference/AI経営組織のつくり方_2026-06-28.md` を先に見るべき条件などが書かれている)
3. **Vault直下の `00_START_HERE.md`**(ツールごとの役割分担・基本フロー)
4. **MARKELINE関連の作業をしている場合のみ**: `/Users/fujiwaraikki/Documents/New project/MARKELINE_Codex_Context/`
   配下のMarkdownを確認してからでないと、MARKELINE関連のコード・LP・資料構成・社内文面は作らない。
   読めない場合は「読めなかったため確認が必要」と明記し、絶対に勝手に断定しない。
5. AIチームの役割分担・スキル設計・運用フロー設計に関わる作業をしている場合は
   `02_reference/AI経営組織のつくり方_2026-06-28.md` を先に確認する。単発の指示処理ではなく、
   役割・判断基準・参照資料・確認ポイントの設計を優先する考え方に合わせる。

## Session_log.mdへの追記フォーマット

新しいファイルを作らない。既存の `03_handoffs/Session_log.md` の末尾に、次の形式で追記する。

```markdown
## YYYY-MM-DD — <プロジェクト名>: <一行タイトル> (<書き込んだツール: Claude Code / Codex>)

### 事実
- 実際に確認・実施したこと

### 仮説
- 確定していないが、そう考えられること(「仮説」であることが分かるように書く)

### 確認事項
- ユーザー本人に確認してもらう必要がある未確定事項(無ければ「特になし」)

### 触ったファイル
- `path/to/file1`
- `path/to/file2`
```

- 「事実」「仮説」「確認事項」は空でも見出しごと残す(何もないことを明示するため)。
- タイトルの `<プロジェクト名>` には、今どのリポジトリ・案件で作業していたかを書く(例: `lstep-portal`)。
- 1回の追記は簡潔に。詳細はコード側のコミットメッセージやPRに書いてあるので、ここでは要点と判断理由だけ。

## 安全ルール(Vault直下のAGENTS.md/Cowork Instructionsより)

- APIキー、パスワード、トークンをMarkdownやコードに直接書かない
- 個人情報、会員情報、未公開の顧客情報を増やさない
- 独自のパスワード認証やメール認証を作らない(コード変更を伴う作業の場合)
- 社外公開アプリを作る場合は、Next.js / Cloudflare Workers / Cloudflare D1 / Cloudflare Access / Claude Opus 固定
  という親プロジェクト側の技術選定ルールがあることを念頭に置く(実際にその作業をする場合は親プロジェクトの
  AGENTS.mdを直接確認する)
- `wrangler.jsonc` の `preview_urls` は必ず `false`(該当作業をする場合)
- GitHubリポジトリはPublicにしない
- AIが生成した内容はすべて下書き・仮説として扱い、断定しない。重要な判断は「事実」「仮説」「確認事項」に
  分けて書く

## Codex CLIから見たときの注意

Codex CLIはこのファイルを `AGENTS.md` 経由で読む。ツールの呼び出し方(スラッシュコマンドやSKILL.md形式)は
Claude Code特有のものだが、判断基準・Vaultパス解決・Session_log.mdへの追記フォーマットはツールに依存しない
ので、そのままこのファイルの内容に従えばよい。シェルスクリプト `scripts/resolve-vault-path.sh` はどちらの
ツールから実行しても同じように動く。
